# ADR-0019: GitHub Actions with pinned, least-privilege workflows

Status: accepted
Date: 2026-08-05

## Context

The repository is on GitHub and accepts fork pull requests. CI for a security tool is itself a
security boundary: a compromised workflow can publish a malicious release to every user. OWASP Top
10:2025 now ranks **A03 Software Supply Chain Failures** third, promoted from 2021's "vulnerable and
outdated components".

## Decision

**GitHub Actions, hardened per GitHub's own security-hardening guidance**, verified 2026-08-05.

### Hardening rules, all enforced

| Rule | Why |
| --- | --- |
| **Third-party actions pinned to a full-length commit SHA** | GitHub's documentation states this is "currently the only way to use an action as an immutable release". Tags are mutable |
| **`GITHUB_TOKEN` read-only by default**, elevated per job | Repository setting plus `permissions: contents: read` at workflow level |
| **No `pull_request_target` on fork PRs** | It runs with repository write access and secrets in a fork's context. The classic total-compromise path |
| **No secrets exposed to fork-originated workflows** | Possible because CI needs **zero cloud credentials** ([ADR-0017](0017-testing-strategy.md)) |
| **No `${{ github.event.* }}` interpolated into `run:`** | Script injection. Values pass through `env:` and are quoted |
| **OIDC for any cloud auth**, never long-lived secrets | Short-lived, scoped tokens; trust policy scoped on `sub` (repo + ref), not `repo:org/*` |
| **PyPI Trusted Publishing (OIDC)** | Exchanges a CI identity token for a PyPI token valid **15 minutes**. Eliminates the long-lived `PYPI_API_TOKEN` secret entirely. Non-negotiable for releases |
| One secret per value, never structured blobs | GitHub's masking works per value; a JSON blob defeats it |

### Pipelines

**On every pull request** (fully offline, no credentials, safe for forks): `ruff format --check`,
`ruff check`, mypy strict, import-linter, unit + policy + determinism + adapter-conformance tests,
integration tests against a PostgreSQL service container, API tests, Schemathesis against the
generated OpenAPI, frontend typecheck/lint/build, generated-client diff check, demo end-to-end scan,
`pip-audit`, secret scan, **fixture credential-pattern check**, **read-only proof**, ADR index check,
and the compliance-text check.

**On merge to `main`**: the above, plus container build and Trivy image scan.

**On tag**: build, SBOM, attestation, publish the wheel via Trusted Publishing.

### SBOM and provenance

- **`anchore/sbom-action` (Syft)** produces one SBOM covering **both** Python and npm dependencies —
  simpler than running `cyclonedx-py` and `cyclonedx-npm` separately and merging.
- **`actions/attest`** for the provenance attestation. Note `actions/attest-sbom` is **deprecated** in
  favour of `actions/attest`; it continues as a wrapper for a period, but new work targets `actions/attest`.
- Target **SLSA v1.2 Build L2** — signed provenance from a hosted build platform, which GitHub-hosted
  runners plus attestation give essentially for free. L3 (via the SLSA generator reusable workflow) is
  a follow-up. **We do not claim a SLSA level on the basis of attestations alone**, because GitHub's
  documentation does not state one.

### Scanning

`pip-audit` (PyPA, Python dependencies) on every PR; **Trivy** on the container image, which also
covers IaC and secrets — thematically apt for a CSPM. Dependabot for update PRs
([ADR-0022](0022-dependency-management.md)).

## Rejected alternatives

- **GitLab CI, CircleCI, Jenkins.** The repository is on GitHub; a second system to authenticate and
  maintain for no benefit.
- **Pinning actions to tags or `@v4`.** Mutable. This is the supply-chain attack that has actually
  happened to Actions users.
- **Running provider tests against real cloud accounts in CI.** Would require storing four sets of
  cloud credentials in a public repository's CI — the exact anti-pattern this product detects. Also
  makes fork PRs impossible to run safely.
- **A long-lived `PYPI_API_TOKEN` secret.** Trusted Publishing removes the secret entirely.
- **Self-hosted runners.** Fork PRs on self-hosted runners execute untrusted code on your
  infrastructure, and self-hosted runners generally cannot reach SLSA L3's isolation requirements.
- **Auto-merging dependency updates.** For a security tool, a dependency change is a supply-chain
  event and gets human review ([ADR-0022](0022-dependency-management.md)).

## Consequences

- Pinned SHAs mean action updates arrive as reviewable Dependabot PRs — more noise, and the noise is
  the point.
- CI is entirely offline and therefore fast and deterministic, and fork PRs run the full suite safely.
- Provider API drift is not caught by CI ([ADR-0017](0017-testing-strategy.md)); accepted and recorded.
- Release requires the tag workflow to succeed end to end, including SBOM and attestation. A release
  cannot be published by hand — which is the intent.
- Contributors see a long check list on every PR. Each check exists to prevent a specific failure, and
  `CONTRIBUTING.md` explains what each one is for.
